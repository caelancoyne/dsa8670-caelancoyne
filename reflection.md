### Reflection File

Before beginning this program I'd often find myself ending up in random repos while researching projects that were well out of my depth, and it's interesting now to see exactly how the structure actually works. For the most part, the very basics that are covered in this week's readings are well-respected by most everyone I've seen that uses GitHub for either professional and personal use. The inclusion of an informative README, some level of thought-out file organization, and attention to version management is encouraged by the GitHub layout, but not strictly required, and yet there's an overwhelming majority of folks out there that commit to following along and playing by the unwritten rules. Like most of what we tend to learn in this program, the reading seems to indicate that there is a bit of a 'language' when it comes to using GitHub, and fluency comes with practice. Learning how to navigate repositories will, I suspect, become easier over time. For now though, bite-sized pushes within a very low stakes environment like editing .txt files to resolve self-inflicted issues is an approachable way to get hands on with the GitHub ecosystem. 

While none of the objectives this week were particularly challenging, I did mindlessly commit my first edits to the intro.txt file without adding a description. Again, this is a low-stakes environment so having to go back through and re-commit everything wasn't a massive time sink, but it was a helpful reminder that the structure here is built around making sure commits and pushes are checked and double checked before they reach your final product. Luckily it was just a couple recommits and remembering which degree program I'm in here, but in the future I can only imagine that these checks will be immensely useful for comparing work with others. Especially in a production environment when there are often real consequences, letting others observe what you're trying to edit before making significant changes to code seems like it'll be incredibly useful. It's popped up in the course through nearly all of the discussions on the analytics lifecycle, but being able to stop, ensure that whatever is being changed is not only safe but relevant to the task at hand, and then push it once it's been reviewed, is absolutely going to keep projects organized and on the correct track going forward.
